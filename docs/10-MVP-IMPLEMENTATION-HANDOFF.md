## Product and shared system contract
- One shared post mechanic: organic-only `PublishOrganic {templateId}` or campaign-tagged `PublishPost {runId,templateId}`. Both pay organic Cuan **once on confirmed settlement**; only a tagged post advances the accepted mission. `ClaimMission {runId}` awards its fixed bonus once. One global `profile.pendingPost`; only one active mission. Full flow/contexts: `02`.
- Public `Catalog.Missions` contains `missionId,requiredImpact,reward,minTier,unlockClaims,templates[3],contexts[]`; `Catalog.OrganicContexts` contains `contextId,trendId,audienceId,clueKey,templates[3]`; `Catalog.Devices` contains `id,order,price,deviceYield,revealSeconds,modelId`; `Catalog.Tiers` and desks/workers own costs and gates. Catalog fields are published to clients **without** strong-choice affinity tags. `ScoringCatalog` server-only matches trend/audience tags using `2*trendMatch+audienceMatch`, rejects ties and computes fit. V0 has one food/organic context; M1 has three organic + three for each four missions. Stable ordered IDs and first winners live in `02`.
- Pure `Rules.postImpact(B,fit,deviceYield)` gives strong `floor(B*1.20*yield)` or weak `min(floor(B*.75*yield),ceil(B*.94),B-1)`; `Rules.organicCuan(fit,deviceYield)` gives `floor(12*(1.25|.75)*yield)`; `Rules.eligibleTier(lifetimeEarned,completedMissions,maxShippedTier)` uses both counters and a shipped cap. V0 cheap/fast: yield1/1.6, reveal18/16, phone price50. M1 PC Rumah price220, yield2.5, reveal13; desk1 180/hire1 500; desk2 250/hire2 750; trainee1.5/s each; tier1 300/3, tier2 1600/3. No laptop, M2 price, random score or payout on click.
- v1 `Profile` contract in `03`: wallet/lifetime/claims/device, property `bedroom`, `ownedDesks` slots1..2, distinct workers, fractional income, bounded claimed-run ring and <=32 saved successful `recentMutationOutcomes`, per-mission variant counters, nextOrganicSequence, activeMission, **one global pendingPost**, ten own summaries and nextPostSequence. Envelope carries schema/revision/lastSaveOpId/lease. This is pre-implementation schema design, not a data migration. A confirmed organic settlement, claim, buy, hire or worker bank needs a conditional save before visible spendable balance; unbanked worker preview is separate and may lose <=30s on crash. Piggyback worker credit/lease renewal on required writes; idle bank <=30s, lease renewal90s/expiry240s; failed load never seeds blank.
- Three `RemoteEvent`s `Command`, `Reply`, `Snapshot` and exact GameTypes unions/payloads/codes in `03`. Server identifies actor from event, validates the exact server-owned `DashboardPromptAnchor` within12 studs, loaded profile/lease, and current dashboard session for economic commands. Server prompts cause `Snapshot:FireClient(player,{kind="OpenComputer",dashboardSessionId=...,expiresAt=...,serverTime=...,state=...})`, **not** a fourth remote. `GetSnapshot` uses a fresh command ID and optional `lookupRequestId` naming an earlier mutation; identical original-ID retry is not a new query ID. `Snapshot` discriminates State/OpenComputer/OpenComputerDenied/ComputerSessionExpired; expiry at 10min idle rejects new session-bound commands with `SESSION_EXPIRED`, does not cancel already-admitted saves and never reopens UI from a late reply. Screen state contains banked balance, pendingWorkerCuan, incomePerSecond, nextOrganicContextId, activeMission/pendingPost, device, ownedDesks/workers. No raw score/price/timestamp/client text crosses as authority. World has `OldCRT` at `TerminalSlot` (dashboard only), the equipped cheap/fast phone at `PhoneSlot` (production) and the room-owned `DashboardPromptAnchor`. BuzzerOS opened on CRT can publish; **server `profile.deviceId` alone determines income/reveal**. PC Rumah replaces CRT and becomes the sole productive device; phone becomes inert. The bedroom has two paid worker slots.
