# Buzzer Simulator — Technical Architecture

## Deployment shape and preserved boundaries
V0 is an internal prototype. M1 is a closed-beta candidate after PC Rumah and two paid worker stations pass their gates; neither milestone automatically authorizes wider publication.
One Roblox place, configured for **one player per game server** in Creator Dashboard.[15] This is product capacity, not authorization: reconnect can overlap across servers. Each `UserId` owns one server-authoritative profile with conditional `UpdateAsync` saves and a time-limited lease. Client handles BuzzerOS/Buzzline/input; server owns post results, organic Cuan, mission bonuses, device/shop prices, workers, tier, physical room, and persistence. No external service, runtime AI, MemoryStore, or database outside Roblox for M1. Conditional writes, budget/backoff, and isolated Studio development data remain mandatory.[1][2][3]

```text
Stable desk-terminal prompt -> WorldService validates character/distance -> Snapshot.OpenComputer -> ScreenGui
ScreenGui -> Command RemoteEvent -> NetRouter validates actor/envelope/session
                                  -> SessionService serializes one player's actions + worker ticks
                                  -> MissionService / EconomyService compute pure profile mutations
                                  -> ProfileStore conditionally persists durable operations
                                  -> Roblox DataStore
WorldService clones owned bedroom/devices/desks; Snapshot/Reply drives HUD/BuzzerOS
```

The initial old CRT is a **non-productive BuzzerOS access terminal** at a fixed prompt. BuzzerOS opened there may initiate `PublishOrganic` and `PublishPost`; the server derives post impact, organic Cuan and reveal time **only** from the confirmed `profile.deviceId`, never the terminal model or client-supplied device data. The owned cheap phone is the only starting production device; fast phone increases its yield; buying PC Rumah replaces the CRT at that terminal and becomes the sole production device. BuzzerOS layout follows actual viewport size, not the equipped device. Rojo v7.4+ maps `.luau` sources and reviewed `.rbxmx` prefabs.[8][13][14] `rojo build -o build/BuzzerSimulator.rbxlx` is a static build, not a playtest.[12] Do not sync arbitrary Studio-owned Workspace children.

## Network contract
Exactly three `RemoteEvent`s under `ReplicatedStorage.BuzzerRemotes`: `Command` (client -> server), `Reply` and `Snapshot` (server -> **that** client via `FireClient`, never `FireAllClients`).[5] `Command` envelope is `{requestId: ASCII 8..64, action: enum, payload: bounded exact-shape dictionary, dashboardSessionId?: string}`. Every new command has a fresh `requestId`. Economic actions and `CloseComputer` require the current `dashboardSessionId`; `GetSnapshot` has no session ID and is allowed while the dashboard is closed. `Player` comes only from `OnServerEvent`. `Reply` is `{requestId, ok, code, revision, serverTime, dashboardSession?:{dashboardSessionId,expiresAt}, data?}`; retain existing codes and add `SESSION_EXPIRED`. The optional session metadata reports the **current** open session/deadline even for `GetSnapshot`; it never opens UI or extends idle time. The sanitized `ProfileSnapshot` is `{revision,serverTime,balance,pendingWorkerCuan,incomePerSecond,lifetimeEarned,completedMissions,tier,maxShippedTier,deviceId,ownedDesks,workers,activeMission?,pendingPost?,nextOrganicContextId,ownPosts,feedVersion,saveStatus}`. Confirmed `balance` alone is spendable; no lease token, private scoring tags or other player's data is sent.

**GameTypes network union (IC-0):** `CommandEnvelope = GetSnapshotCommand | SessionCommand`. `GetSnapshotCommand = {requestId:RequestId, action:"GetSnapshot", payload:{lookupRequestId?:RequestId}}` with **no** `dashboardSessionId`. `SessionCommand = {requestId:RequestId, action:"AcceptMission"|"PublishOrganic"|"PublishPost"|"ClaimMission"|"BuyDevice"|"BuyDesk"|"HireWorker"|"CloseComputer", dashboardSessionId:string, payload: exact action shape below}`. `SnapshotEvent` is the discriminated union `{kind:"State", state:ProfileSnapshot}`, `{kind:"OpenComputer", dashboardSessionId:string, expiresAt:number, serverTime:number, state:ProfileSnapshot}`, `{kind:"OpenComputerDenied", code:"NOT_READY"|"OUT_OF_RANGE"|"SAVE_UNAVAILABLE"|"INVALID_STATE"}`, `{kind:"ComputerSessionExpired", dashboardSessionId:string, reason:"IDLE"|"CHARACTER_LOST"}`. `Reply.data` for `GetSnapshot` is `{snapshot:ProfileSnapshot, lookup?:{originalRequestId:RequestId, status:"APPLIED"|"REJECTED"|"PENDING"|"UNKNOWN", originalResult?:{ok:boolean, code:string, revision:number, data?:sanitized result}}}`. `lookup` is absent without `lookupRequestId`; `originalResult` is present only for APPLIED/REJECTED. Other replies carry their action-specific sanitized result. `dashboardSessionId` is an ephemeral server-generated bounded UI generation identifier, **not** an authorization token; actor, prompt and server-side session are separately validated. The snapshot's `revision` guards state updates; `dashboardSessionId` guards stale open/expiry/close messages, not DataStore revisions. `Reply.dashboardSession` can refresh a matching client watchdog but cannot reopen the UI.

| Action | Payload | Server checks and effect |
|---|---|---|
| `GetSnapshot` | `{lookupRequestId?: requestId of original mutation}` | Fresh command `requestId`; loaded profile, throttle; optionally look up original outcome; when write lane is busy, return last **confirmed** snapshot and current lookup status without waiting (PENDING only if that ID is reserved); otherwise may settle an already-due post through durable lane; creates no new post/purchase/claim |
| `AcceptMission` | `{missionId}` | Unlocked/available, no active run; assign/freeze next catalog context; durable save |
| `PublishOrganic` | `{templateId}` | Next organic context from server sequence, exact template, no global pending post; freeze outcome and durable save |
| `PublishPost` | `{runId,templateId}` | Active accepted run, context/template match, postCount < 2, no global pending; freeze outcome and durable save |
| `ClaimMission` | `{runId}` | Settle due post first; ready, same run, unclaimed; fixed bonus and claim count persist once |
| `BuyDevice` | `{deviceId}` | Exact next cheap -> fast -> PC, price/ownership/server tier/funds; save and sync world |
| `BuyDesk` | `{slotIndex: integer}` | Index 1 or 2; owned PC, tier, vacant sequential room slot, server price; save and sync world |
| `HireWorker` | `{slotIndex: integer, roleId: "trainee"}` | Index 1 or 2; paid desk, tier, free slot, worker cap 2, server price; save and sync world |
| `CloseComputer` | `{}` | Matching current dashboard session; server closes it without a DataStore write; client restores movement/camera immediately, not after reply |

**OpenComputer delivery:** `WorldService:ValidateDashboardPrompt(player,prompt)` handles server-side `ProximityPromptService.PromptTriggered` on the stable `DashboardPromptAnchor`; server rechecks that this exact server-owned prompt belongs to the player's room, the player has a loaded/writable profile and living character within 12 studs, and the lease is valid.[4][7] On acceptance it creates a **new** server-owned dashboard session generation (10-minute idle deadline; invalidates any older generation; no DataStore write), calls `Snapshot:FireClient(player, {kind="OpenComputer", dashboardSessionId=..., expiresAt=..., serverTime=..., state=sanitizedSnapshot})`; **there is no `OpenComputer` RemoteEvent and no client `OpenComputer` Command**. Invalid prompts do not create/extend a session; `Snapshot:FireClient` sends `OpenComputerDenied` with the bounded reason, and the client may toast but must not change camera/input. Client transitions camera and displays BuzzerOS **only** for a new live `OpenComputer`, never for a plain `State` snapshot or an ID already closed locally. If a valid new generation arrives while BuzzerOS is already open, replace the generation without overwriting the original pre-open camera/input restore snapshot.

**Timeout and idempotency:** On a 6-second mutation timeout, keep the original ID `mut-0001` and block other new mutations. Send `Command {requestId="qry-0002", action="GetSnapshot", payload={lookupRequestId="mut-0001"}}` using a **new** query ID. `Reply.requestId="qry-0002"` correlates the query; `data.lookup.originalRequestId="mut-0001"` identifies the original, not the query. The query returns current state and APPLIED (durably successful; original result in persisted window), REJECTED (definite error cached live), PENDING (in-flight reservation/write), or UNKNOWN (no evidence; **not** proof of non-application). APPLIED/REJECTED resolves the original without another credit. PENDING waits/requeries; the client may retransmit **the original identical mutation envelope with `requestId="mut-0001"`** while its in-flight reservation remains live in the same dashboard/server session. Reserve the ID before the per-player lane; concurrent arrivals with that ID join the same in-flight result, and completed IDs replay the cached result without re-execution. UNKNOWN is **always unresolved**, including in the same session: never automatically retransmit or issue a new payout ID because a bounded ring cannot prove non-application. Show a refresh/reopen-required state and reconcile visible ownership/post/claim state. A genuinely new player action gets a new ID only after the uncertain action is resolved or the player deliberately begins a separate action. Worker-bank and settlement operation IDs are server-owned, independent of command IDs; a due settlement triggered by `GetSnapshot` uses the original stable post settlement ID, never `qry-0002`. If an operation already owns the lane, return only the last confirmed snapshot and the lookup's actual status (PENDING only for its reserved ID); schedule any due settlement behind the same lane instead of waiting indefinitely or exposing an uncommitted copy.

`GetSnapshot` and its optional lookup never extend dashboard idle time. Valid session-bound **economic** user actions extend it at admission (even if domain checks later reject insufficient funds); invalid/forged traffic, `CloseComputer`, background polling and worker ticks do not. The server returns the current deadline/ID in `Reply.dashboardSession` after any command; client adjusts its local watchdog from `serverTime`/`expiresAt` **only if the ID matches the currently open UI**, not from an old replayed result. At 10 minutes of user-action inactivity the shared scheduler expires the session and sends `ComputerSessionExpired` once; character loss does likewise, and leave clears it. On expiry the server rejects **new** session-bound commands with `SESSION_EXPIRED`, and may resend the expiry notification; an already-admitted mutation finishes/reconciles even if expiry occurs while saving. The client immediately disables economic controls, closes UI and restores its pre-open camera, input, movement and focus exactly once on expiry, local expiry watchdog, Close, death or respawn. A `GetSnapshot` (fresh ID) and late `Reply` may still refresh HUD/pending reconciliation, but neither reopens BuzzerOS. Only a fresh validated prompt opens it again; a stale `CloseComputer` or economic command from the old `dashboardSessionId` cannot close or execute inside the new session. Preserve unresolved mutation IDs across UI closure; no automatic reissue on reopen.

Rate-limit command traffic (initial 8/s/player, publish >=2s apart), validate bounded exact shapes/ASCII strings, and reject extra keys, invalid types, unknown IDs, non-finite values, foreign identity, prices, totals, timestamps and worker rates from client.[4] A live cache/reservation plus a **persisted bounded 32-entry successful mutation-outcome ring** supports lookup after reconnect; persist the outcome in the same conditional write as the mutation. Definite validation errors may be cached live without a write, so after reconnect their lookup can be UNKNOWN. Evicted entries are UNKNOWN, not evidence that retry is safe. Claim/purchase guards and stable post/settlement IDs give additional protection; they do not justify replaying an unknown organic post after reconnect.

## Post, mission, and feed lifecycle
One `profile.pendingPost` for **either** publishing mode: `{postId,mode,missionRunId?,contextId,templateId,publishedAt,settleAt,finalImpact,organicCuan}`. Mission state is `{missionId,runId,contextId,status,accumulatedImpact,postCount}`; state moves as `02` defines. `PublishOrganic` uses `nextOrganicSequence % organicContextCount`, and increments the persisted sequence; `PublishPost` uses frozen mission context. `AcceptMission` assigns `missionVariantCounters[missionId] % availableContextCount`, persists the increment, and freezes the context. First food-stall run gets `meal_time`; catalog IDs/order stay stable for saved runs and replays. No client-chosen context or refresh reroll. An accepted mission can coexist with an organic post; only one pending post exists globally.

Pure `Rules.postImpact(B,fit,deviceYield)` and `Rules.organicCuan(fit,deviceYield)` compute and freeze final outcome on the server **at publish**; organic-only posts use `B=100` for presentation. A publish initiated in BuzzerOS at `OldCRT` still reads the **one** productive `profile.deviceId` (cheap/fast phone until PC purchase, PC afterward); `OldCRT`, `TerminalSlot` and `DashboardPromptAnchor` never contribute yield. Private `ScoringCatalog` stores template trend/audience affinities; `score = 2*trendMatch + audienceMatch`, with each match 0 or 1. Validate a unique highest-scoring template for every shipped context at catalog load; a tie is invalid content, never a random tiebreak. There is no per-post RNG. `Catalog.Devices[deviceId].revealSeconds` sets `settleAt`. The server persists the frozen pending post before `OK`. A due settlement removes pending post, credits organic payout exactly once, adds a bounded own-post summary, and, for a mission post, adds impact and moves accepted/resolving/ready as appropriate. It conditionally persists **before** sending the new balance or success. A failed/ambiguous settlement is retried with one stable operation ID and no re-roll. `ClaimMission` separately persists its one-time fixed bonus; reconnect can settle a due post but **never** grants offline worker pay. Missing claim remains available. `FeedService` projects up to 12 authored cards plus ten own summaries; no per-NPC simulation or raw player content. Engagement animation uses saved impact/server times and fixed authored reply pools, never client-submitted counts.

## Profile and persistence contract
One DataStore key `Player_<UserId>` per player in separate dev/production universes. Proposed **v1 schema has not shipped**; revise it now, before BS-01. No live migration exists. A future schema change requires fixtures and rollback-compatible readers.
```text
profile = {
  balance: nonnegative integer, lifetimeEarned: nonnegative integer,
  completedMissions: nonnegative integer, deviceId: catalog ID,
  propertyId: "bedroom", ownedDesks: array of slot indices 1..2,
  workers: array of {hireId, roleId: "trainee", slotIndex},
  fractionalIncome: number in [0,1),
  claimedRunIdsWindow: <=32 server-generated run IDs,
  recentMutationOutcomes: <=32 {requestId,action,intent,ok:true,code:"OK",revision,resultIds?},
  missionVariantCounters: bounded map of shipped mission IDs to nonnegative integers,
  nextOrganicSequence: nonnegative integer,
  activeMission: nil or {missionId,runId,contextId,status,accumulatedImpact,postCount},
  pendingPost: nil or {postId,mode,missionRunId?,contextId,templateId,
    publishedAt,settleAt,finalImpact,organicCuan},
  ownPosts: <=10 bounded post summaries, nextPostSequence: nonnegative integer
}
envelope = {schemaVersion,revision,lastSaveOpId,updatedAt,profile,
  lease: {token,jobId,expiresAt}}
```
`pendingWorkerCuan` is **ephemeral** until banked; do not persist an unconfirmed claim as spendable balance. A credit window has deterministic `elapsed`/fractional carry under the same mutation lane; on a command, include pending worker accrual in the conditional save and publish it only after success. Keep a bounded saved `updatedAt` for diagnostics/lease, **not** offline earnings. Validate every ID, array/map bound, finite timestamp/amount, integer cost, ownership and cross-field state. A missing prefab must not silently leave a permanent paid-but-unrepairable world; world re-syncs from saved IDs on rejoin and surfaces a presentation error. Never store NPC catalogs or part references in profile.

**Durable mutations:** `AcceptMission`, either publish, due settlement, claim, buys, hires, and a 30-second worker bank save must be confirmed via conditional `UpdateAsync` before their payouts/ownership enter confirmed UI. Persist a successful client mutation's bounded lookup result in `recentMutationOutcomes` **in that same write**; `intent` is the canonical bounded action+payload, and `resultIds` contains only the minimal post/run/purchase identity needed to replay its result. An identical request ID with **different** action/payload is `INVALID_INPUT`, not a replay. Server-owned settlement/bank operation IDs stay in the existing last-save/settlement reconciliation path, not in the client-request ring. A command mutates a deep copy non-yieldingly, writes through ProfileStore, then swaps published state. A definite failure retains prior live profile; ambiguous write reconciles by stable operation ID and uncached read, otherwise freezes actions with `SAVE_UNAVAILABLE`. Worker preview can be lost in a crash up to one unsaved window; label it separately. Lease renewal every 90 seconds even without economic changes; expiry 240 seconds. Check read/write budgets and use bounded jittered retries.[1][3]

**Lease:** Atomically acquire on load if absent/expired or same token, else `LOCKED`. `UpdateAsync` callback compares lease token and expected revision; if operation ID is already the last saved ID, return unchanged envelope. Otherwise verify validated immutable snapshot, increase revision once, write operation ID, renew lease. Serialize writes per player; never yield in callback or mutate an in-flight snapshot. Clean leave uses a conditional final bank/save/release and stable operation ID; `BindToClose` is best effort. A competing token cannot overwrite this token. After ambiguous response, retry with same ID/snapshot, then read without cache; never invent success. On lease loss or repeated failure, block economic commands/confirmed payouts and stop accrual. Failed load never seeds an empty replacement; unsupported/future/corrupt data remains untouched. Pure sequential migrations only after reviewed fixtures. Studio API access enabled **only** in an unpublished dev universe.[2][3][10]

## Income, concurrency, and invariants
One shared scheduler iterates loaded players near 1 Hz. Use monotonic connected-session elapsed time: process in bounded `dt<=60`-second chunks and retain any remainder for the next lane turn, so a long save or frame hitch does not silently discard connected time. Credits `floor(fractionalIncome + 1.5*workerCount*dt)` with residual; aggregate per player, no per-worker coroutine. Worker accrual enters the **same serialized per-player lane** as commands/settlement/save; any time spent waiting on a durable write is credited when the lane resumes, not lost or double-counted. Fold accrued worker credit into the **next already-required durable economy write**; the 30-second bank scheduler writes only when no such write has banked it. Lease renewal piggybacks on these writes. On quit save what can be saved, with no offline catch-up. A snapshot shows confirmed `balance` and unbanked preview separately; confirmed balance is monotonic except purchases. Server pushes at most every 2 seconds while active; client never predicts spendable credits.

## DataStore write-pressure envelope (planning, not a measured quota)
One confirmed `UpdateAsync` per accepted `AcceptMission`, publish, settlement, claim, purchase or hire. Opening/closing BuzzerOS, ordinary snapshots, lookups and rejected requests add **zero** writes; `GetSnapshot` can still cause the **one existing due settlement**. Connected worker banking adds at most one write per 30 seconds **only if not already folded into another durable write**. An otherwise idle profile needs a lease renewal at most once per 90 seconds; worker banks piggyback it. Under the `04` modeled PC cycle times, organic-only: `2*60/25=4.8` writes/min; repeated strong campaign: `4*60/65=3.69` writes/min; alternating organic/campaign: `6*60/90=4` writes/min. With workers, piggyback usually adds zero while posting; conservative no-piggyback upper bounds add 2/min. Each purchase/hire is +1 write in its minute. Reveal-only lower bounds without reading/latency imply PC organic `2*60/13=9.23` and strong campaign `4*60/13=18.46` writes/min before worker banks; this is a **stress case**, not expected player throughput.

Current Creator Hub standard-store server budgets start at `60 + 40*numPlayers` per minute separately for read/write; `UpdateAsync` consumes both, and experience-wide and per-key throughput/partition limits also apply.[3] One-player nominal server budget is 100/min; it is **not** a per-key latency guarantee. A hot single key, bursty accept/settle/claim/save, ambiguous retries or throttling can queue writes even below that nominal count. Measure `UpdateAsync` attempts/success/errors/latency, oldest queued operation age, payload bytes, `StandardRead`/`StandardWrite` available budget and last confirmed revision in an isolated dev universe. Retain one per-player serialized write lane, bounded queue and `BUSY`/`SAVE_UNAVAILABLE` backpressure; do not acknowledge uncommitted Cuan or batch distinct payouts asynchronously merely to raise throughput. Merge only worker bank/lease renewal into an **already-required** durable mutation. If measurements show key pressure, consider a measured admission interval; do not preemptively change the 18/16/13-second reveals or the modeled economy. Fake-store tests must impose configurable single-key service delay and transient/throttle/ambiguous failures, then assert bounded queue, no double credits, confirmed-before-display, healthy 30s bank and saved-result replay. A real dev-universe sustained scenario records attempted/confirmed writes, budgets, p50/p95 latency and failed/retried outcomes before any release gate.

Invariants: balance >=0; lifetime increases only by confirmed credits; one global pending post, no more than one active mission, no more than two campaign posts/run; each `postId` pays organic Cuan at most once and each claimed `runId` pays mission bonus once; workers occupy distinct paid slots 1..2 and require PC; tier cannot demote after spending; device yields never stack; save revision changes only after successful conditional writes. Cap economic totals below `1e12`. Test reordered, duplicated, timeout, death, disconnect/reconnect, overlapping-server, and failed-write cases. No multiplayer feature follows merely from one-player server ownership hygiene.

## World and interface ownership
`WorldService` clones a reviewed bedroom prefab into a per-player Workspace folder; stable `PlayerDesk/DashboardPromptAnchor/TerminalSlot/PhoneSlot/WorkerDeskSlot1/2/WorkerSeat1/2` anchors are server-owned. V0 shows `OldCRT` at `TerminalSlot` (BuzzerOS access only) and the equipped cheap/fast phone at `PhoneSlot` (production); M1 PC Rumah replaces `OldCRT` at `TerminalSlot` and becomes the **only** production device, with the owned phone left as an inert prop. The prompt stays at `DashboardPromptAnchor`; the new PC cannot collide with the player or invalidate it. Room property remains `bedroom` through M1. `App.client.luau` creates safe-inset ScreenGuis in `PlayerGui`, temporarily focuses camera toward the terminal when BuzzerOS opens, and restores camera/input/movement on close, death, expiry and respawn.[6][11] Worker rigs are local ambient visuals; a failed animation cannot halt server income.
